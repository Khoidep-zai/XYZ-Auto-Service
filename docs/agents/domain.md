# Domain docs

This is a single-context repo. The domain glossary belongs at the root in `GLOSSARY.md`; architecture decisions belong in `docs/adr/`.

Before exploring a code area, read the glossary and ADRs relevant to it. If either is absent, proceed without flagging it. Create these files when domain terms or decisions are actually resolved.

Use terms defined by the glossary in issues, proposals, hypotheses, and tests. If a needed concept is missing, reconsider the term or note the gap for `/domain-modeling`.

If proposed work conflicts with an ADR, identify the conflict explicitly rather than silently overriding the decision.
